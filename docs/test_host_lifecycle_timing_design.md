# Linux Test Host Lifecycle Timing Design

## Goal

Measure where time is spent on Linux Taskcluster test hosts, especially
time outside task execution. The first implementation favors local data
collection and offline analysis over centralized metrics.

The initial scope is deliberately limited to the normal single-task Linux
worker lifecycle. Other platforms and centralized ingestion can use the
validated event model later.

Implementation belongs in a small `linux_host_lifecycle` Puppet module. That
module owns the logger executable, storage directory, sudoers rule, and
logrotate policy. The existing `puppet` and `linux_generic_worker` modules
only invoke the logger at their lifecycle hooks. The same module contains the
offline pilot analyzer in a non-deployed `tools/` directory, alongside the
logger's implementation and tests.

`lifecycle-log` is a Python 3 program using only the standard library.
Parser tests use small synthetic or sanitized syslog fixtures containing only
representative `WORKER_METRICS` lines; raw host logs are not committed because
they may include task environment and credential material.
Tests use Python's built-in `unittest` runner, avoiding an additional test
dependency. They cover JSONL append behavior, duplicate metric imports,
current-boot filtering, rotated-log fallback, and report aggregation.

## Approach

Each host maintains a local append-only JSON Lines event log. Logs are
collected over SSH and merged for offline analysis.

The design records facts, rather than durations or conclusions. Analysis
computes durations and identifies incomplete lifecycles after collection.

## Event Model

Every event contains these common fields:

```json
{
  "schema_version": 1,
  "event": "worker_started",
  "recorded_at": "2026-08-05T23:03:14.123Z",
  "host_id": "example-host",
  "boot_id": "Linux boot ID",
  "event_id": "UUID generated by lifecycle-log",
  "source": "lifecycle-wrapper"
}
```

`host_id` and `boot_id` associate events with a particular host and boot.
`event_id` identifies the particular locally written JSONL record, allowing a
collector to safely deduplicate repeated transfers without maintaining a
per-boot counter.

`host_id` is the Linux hostname. This matches the Taskcluster `workerID` and
the name operators use for SSH collection.

Events extracted after the fact from generic-worker logs also contain:

```json
{
  "event_time": "2026-08-05T23:01:12.000Z",
  "recorded_at": "2026-08-05T23:03:14.123Z",
  "source": "generic-worker-log",
  "parser_version": 1,
  "source_record_id": "stable worker-metric identity"
}
```

`event_time` is the original generic-worker log timestamp, while
`recorded_at` is when the importer wrote the lifecycle event. This
distinction prevents delayed parsing from looking like delayed worker
readiness or task start. The structured generic-worker metrics provide
whole-second epoch timestamps, so any measurement involving an imported event
has one-second source resolution; reports do not claim sub-second accuracy for
those intervals.

## Initial Events

The initial Linux event set is intentionally small:

| Event | Source | Meaning |
| --- | --- | --- |
| `boot_started` | Linux boot metadata observer | The current kernel boot began; its event time comes from current-boot metadata. |
| `puppet_run_started` | Explicit `run-puppet.sh` hook | The first Puppet attempt for this boot is about to begin. |
| `puppet_run_succeeded` | Explicit `run-puppet.sh` hook | Puppet has succeeded and the worker-start sentinel is about to be created. |
| `worker_started` | Explicit wrapper hook | The wrapper is about to invoke `start-worker`. |
| `worker_ready` | generic-worker log import | generic-worker reached the selected, documented ready marker. |
| `task_started` | generic-worker log import | generic-worker log evidence identifies a task run beginning. |
| `task_finished` | generic-worker log import | generic-worker log evidence identifies that task run completing. |
| `worker_exited` | Explicit wrapper hook | `start-worker` returned to the wrapper; includes its exit code. |
| `restart_executed` | Explicit wrapper hook | The wrapper has reached the point where it invokes the reboot command. |

Task events include `task_id` and a task run or attempt identifier when the
generic-worker record provides one. The initial `task_finished` event has no
outcome field: the structured `taskFinish` metric does not include one.
`worker_exited.exit_code` describes the worker process exit and must not be
interpreted as the resolved task outcome.

`restart_executed` records that the reboot command was invoked; it does not
claim that reboot completed. A subsequent `worker_started` with a new
`boot_id` establishes that the host returned and began launching the worker.

The normal lifecycle is:

```text
boot_started -> puppet_run_started -> puppet_run_succeeded -> worker_started
    -> worker_ready -> task_started -> task_finished
    -> worker_exited -> restart_executed -> worker_started (new boot_id)
```

The sequence is not a success criterion. Missing events are expected for
worker crashes, host failures, quarantine, operator holds, and collection
before a lifecycle has completed.

## Logger and Generic-Worker Importer

One small `lifecycle-log` tool provides two separate responsibilities:

```text
lifecycle-log emit worker_started
lifecycle-log emit worker_exited --exit-code 0
lifecycle-log emit restart_executed --trigger post_task
lifecycle-log observe-boot
lifecycle-log import-generic-worker
```

`emit` is deliberately simple: it writes a fact at the current time and
automatically supplies the host, current Linux `boot_id`, and an `event_id`.

`observe-boot` reads the current Linux boot metadata and idempotently records
`boot_started`. Its `event_time` is the kernel boot time and its `recorded_at`
is the time the observer ran. It can be called near the beginning of
`run-puppet.sh`; callers do not construct or pass the boot timestamp.

`import-generic-worker` reads the `generic-worker` records from the local
system log. It parses only the JSON object immediately following the literal
`WORKER_METRICS ` prefix. The supported initial generic-worker versions are
`v61.0.0` and `v88.0.2`; `v61.0.0` is the minimum version. The selected ready
marker is a record whose `eventType` is `workerReady`.

The parser accepts these event shapes, established from sanitized records on
both pilot hosts. All accepted records require string `eventType`, integer
epoch-seconds `timestamp`, string `workerId`, and string `workerPoolId`.
`workerReady` maps to `worker_ready`; `taskStart` maps to `task_started`; and
`taskFinish` maps to `task_finished`. The two task records also require string
`taskId` and integer `runId`, which become `task_id` and the task-run
identifier. The observed `worker`, `instanceType`, and `region` fields are not
used by the initial event model. No other `eventType` is imported.

Their metric timestamps and task/run identities become extracted lifecycle-
event fields; raw generic-worker log content is never copied into the
lifecycle log. The importer records its own parser version.

The importer accepts only metrics whose embedded epoch timestamp falls from
the current boot's `boot_started.event_time` through the import time. This
ties extracted events to the current `boot_id` and avoids relying on the
different syslog timestamp formats used by supported Ubuntu releases.

It parses the active `/var/log/syslog` first. Only if a required current-boot
metric is missing does it inspect `syslog.1`, then older compressed rotations
one at a time. It stops when all expected events have been found or a file is
older than the current boot. This keeps gzip work off the normal path while
remaining correct when syslog rotates during a long-lived worker process.

The importer is idempotent. Each imported source record receives a stable
`source_record_id` derived from its metric type, metric timestamp, worker
identity, task ID, and run ID when present. The importer checks the current
JSONL log and does not write an event already represented by that ID. The ID
remains in the event so offline analysis can also deduplicate records.

The worker wrapper invokes the importer through a narrow sudoers rule that
permits only `/usr/local/bin/lifecycle-log import-generic-worker`, with no
caller-controlled log path or options. This is required because `cltbld` does
not otherwise have permission to read the system log. The root-run importer
extracts only the required structured metric fields.

## Local Storage

The initial JSONL log lives at `/var/log/host-lifecycle/events.jsonl`.
Its directory is owned by `root:cltbld` and writable by that group, so both
root's `run-puppet.sh` hooks and the `cltbld` worker wrapper can append events
without a privileged logging daemon.

Use standard size-based `logrotate`: rotate at 1 MB, retain 39 rotated files,
and compress old files. This bounds raw, uncompressed-equivalent retention at
about 40 MB while retaining the newest records instead of refusing to log
when a fixed limit is reached. The logger opens, locks, appends one JSONL
record, and closes for each event; it does not maintain a long-lived file
descriptor across rotation. It uses an exclusive Linux `flock` for the
open/append/close operation when root's Puppet hook and the `cltbld` wrapper
run concurrently.

Collectors read the active JSONL file and every rotated file, including
compressed archives. They deduplicate events by `(host_id, event_id)` rather
than relying on remote byte offsets or file names, so a repeated or
rotation-raced collection is harmless. A final incomplete JSONL line is
ignored and collected successfully on a later pass.

Pilot collection is manual over SSH. No scheduled collector or centralized
ingestion is part of the initial implementation. A small offline
`tools/collect-lifecycle-logs.py` helper uses the operator's SSH configuration
to collect the fixed remote lifecycle-log directory from requested hosts into
host-named local directories. It uses the system SSH client rather than adding
a `pssh` dependency. Each collection creates a timestamped local snapshot
directory rather than overwriting a previous collection.

The pilot hosts are `t-linux64-ms-015` (Ubuntu 18.04) and
`t-linux64-ms-016` (Ubuntu 24.04). Deployment of the pilot is handled
separately from this design and implementation work.

The initial Puppet deployment scope is
`roles_profiles::roles::gecko_t_linux_talos` and
`roles_profiles::roles::gecko_t_linux_2404_talos`. Their deployed
generic-worker versions are `v61.0.0` and `v88.0.2`, respectively.

Use only synthetic fixtures that preserve the documented metric shapes. Do
not commit raw syslog because it can contain task environment or credential
material.

## Hook Placement

At the beginning of `run-puppet.sh`, call `observe-boot` and then emit
`puppet_run_started`. After Puppet has succeeded and immediately before the
worker-start sentinel is created, emit `puppet_run_succeeded`.

In `run-start-worker.sh`, emit `worker_started` immediately before invoking
`start-worker`. When it returns, first import the current boot's
`generic-worker` system-log records, then emit `worker_exited` with the return
code. On the branch that invokes reboot, emit `restart_executed` immediately
before the reboot command.

Every hook is conditional on `lifecycle-log` being installed. A missing tool
or any non-zero logger/importer exit is non-fatal: it may report an error to
the normal system log, but must not interrupt Puppet, worker startup, task
execution, or reboot.

## Initial Analysis

Only compute a duration when both named endpoints are present and have the
expected host, boot, and task/run relationship:

| Measurement | Calculation | Meaning |
| --- | --- | --- |
| Restart-to-boot | next `boot_started` - `restart_executed` | Time through shutdown, firmware, and the start of the new kernel boot. |
| Early host startup | `puppet_run_started - boot_started` | Startup work before the first Puppet attempt, including existing cleaner services. |
| Puppet run | `puppet_run_succeeded - puppet_run_started` | Time until Puppet succeeds for that boot. |
| Task runtime | `task_finished - task_started` | Time executing a task. |
| Post-task overhead | `restart_executed - task_finished` | Wrapper work after task completion and before reboot invocation. |
| Restart-to-worker | next `worker_started` - `restart_executed` | End-to-end time for host restart and pre-worker initialization. |
| Worker initialization | `worker_ready - worker_started` | Time from launching `start-worker` until generic-worker is ready. |
| Idle/claim latency | `task_started - worker_ready` | Time a ready worker waits before starting a task. |

If an endpoint is missing, the duration is unavailable rather than inferred.
Analysis may classify an incomplete lifecycle only after a defined threshold
and relative to the collection time. For example, a
`restart_executed` event without a new-boot `worker_started` after a chosen
threshold is a possible failed return, not proof of one.

The first pilot report presents p50, p95, and maximum values per host and for
the combined pilot for restart-to-boot, early host startup, Puppet run, worker
initialization, task runtime, and post-task overhead. It also lists incomplete
lifecycle counts and their final observed event. No alert thresholds are set
during the pilot. The offline analyzer performs one aggregation and renders it
as a human-readable terminal table by default, with JSON and CSV output modes
for structured summaries and percentile rows. It calculates p50 and p95 using
the nearest-rank method, which is transparent for the pilot's small samples
and requires no statistics dependency.

## Deferred Events and Enhancements

Do not add an event until it has a concrete Linux hook and a specific
measurement purpose. Candidates include:

- `shutdown_started`, from a best-effort systemd shutdown hook, if splitting
  reboot-command delay from the remainder of the restart cycle becomes useful.
- `cleanup_started` and `cleanup_finished`, once the exact cleanup operation
  to measure is defined.
- Centralized ingestion, dashboards, and alerting after the event model and
  analysis are validated locally.

## Decisions Still Needed Before Implementation

- Define post-pilot thresholds for classifying stale or incomplete lifecycles.
- Decide whether any deferred lifecycle events are worth adding after reviewing
  the pilot report.
